# Молекулы: граф вместо enum — куда идём

> Краткая версия — в [`ROADMAP.md`](../ROADMAP.md). История и обоснования реализованного — в git.


## Цель: движение атомов как ПРЕДМЕТ игры

Растяжение связи, разрыв от натяжения, колебание с настоящей частотой (`ν ~ √(k/μ)` — стык с ИК,
merge-game §7). Всё это требует хранить координаты и скорость **на каждый атом**, а не одну точку на
сущность. Это вариант D из прежнего разбора геометрии (A/B/C/D — в git, коммит `b8823ea`).

**Вращение специально не делаем** — оно приедет само, как только у атомов появятся независимые скорости.

Два решения, отменяющих прежние выводы того разбора:

- **Вариант A (релаксация в `MoleculeGeometry`) снят.** Если ограничения расслабляют форму в рантайме,
  хороший статический раскладчик не нужен — нужна лишь стартовая догадка, нынешняя радиальная годится.
- **Ограничения ПО СВЯЗЯМ (PBD), а не shape matching.** Прежний вывод выбирал shape matching по
  устойчивости, но предмет игры — связь: жёсткость на связь из `BondEnergy`, растяжение на связь,
  ν из k и приведённой массы концов. Shape matching даёт одну жёсткость на всю молекулу и меряет
  деформацию силуэта целиком. Устойчивость у PBD та же (двигаем позиции, а не интегрируем силы).


## Лестница

Обязательная цепочка **3b → 3c → 5 → 6**; пункты 0 и 4 независимы и вставляются где угодно.

| | шаг | состояние |
| --- | --- | --- |
| 1a | `Vec2D` иммутабелен | ✅ |
| 3a | `position`/`direction`/`velocity` → одна `Kinematics` | ✅ |
| ii | `species` и `id` вон из `EntityState`; `Species` удалён целиком | ✅ |
| **3b** | `Kinematics` → `Map<localId, Kinematics>` | **следующий** |
| 3c | свернуть `direction`+`velocity` в один `Vec2D` | |
| 0 | `bondLengthPx` из `covalentRadiusPm` (лежит мёртвым грузом) | независимый |
| 4 | наследование координат через `merge`/`split` | независимый |
| 5 | развязать скорости + решатель ограничений | |
| 6 | геймплей: разрыв от натяжения, колебания | |

### 3b — что именно

`EntityState` держит `Map<Int, Kinematics>`, ключ — `localId` узла графа. Позиции **абсолютные**, не
смещения: иначе центр остаётся вторым источником правды и вопрос «сила приложена к одному атому — центр
поехал?» становится неопределённым. `centerPosition` превращается в центроид (производную). Одиночная
сущность = карта из одного элемента с `localId = 0`.

Засев и проекция пишутся прямо в `Molecule` — у него граф под рукой (ради этого трек (ii) и делался
раньше кинематики). Внутри `Kinematics` поле стоит переименовать обратно в `position`: там будет позиция
одного АТОМА, а `centerPosition` останется только на `EntityState`.

**Инвариант «ключи карты == узлы графа» проверять не надо.** Граф иммутабелен, структурные реакции =
consume + spawn, мутаторы идут через `mapValues` (ключи сохраняются) — набор ключей фиксируется при
засеве и дрейфовать не может. Проверка понадобится на шаге 4, в конструкторе `Molecule`, когда
координаты впервые придут извне.

**DTO сохранения на 3b не меняется**: молекула ещё жёсткая, координаты = центр + смещение из графа, одной
точки достаточно. Формат поедет на шаге 5.

### Цена, которая не лечится переписыванием вызывающих

- **связи придётся держать с первого дня.** У атомов свои скорости — молекула разлетается на первом же
  тике. Явный Эйлер (`applyNewPosition` без `dt`, демпфер `reduceVelocity`) с жёсткой пружиной идёт
  вразнос; в MD поэтому связи делают ограничениями (SHAKE/LINCS), а в играх — проекцией позиций (PBD);
- **`merge`/`split` перенумеровывают узлы**, поэтому наследование координат требует протащить через
  хирургию отображение старый→новый `localId`.

### Откуда у новорождённой координаты (шаг 4)

| рождение | что с координатами |
| --- | --- |
| `PhotoDissociation` / `StarDissociation` | ✓ и ЛУЧШЕ, чем сейчас: `spawnFragments` разводит осколки искусственно по оси X, потому что настоящих координат нет — с наследованием они просто остаются где были |
| `BondStrengthening`, `MolecularPhotoIonization` | ✓ переносятся как есть (у усиления связь в реальности ещё и короче) |
| `CovalentBondFormation` | позиции есть, но атомы стоят на дистанции столкновения, а не на длине связи → нужен доводочный шаг |
| `MoleculeGrowth` | у молекулы ✓, новичка надо ПОСТАВИТЬ в свободный слот со стороны партнёра |
| `RingClosure` | наследовать нечего: кольцо замкнулось, а атомы лежат цепью |
| спавн из `World`, загрузка, молекула из реестра | родителей нет → засев с нуля |

`MoleculeGeometry` не исчезает — меняется её работа: из «форма молекулы» в «засев новорождённых + доводка
после хирургии».


## Ближайшая очередь (не про кинематику)

1. **`Entity.distanceTo(other)`** — между ПОВЕРХНОСТЯМИ по ближайшей паре атомов. `distanceToSurface(point)`
   уже есть и считается по атомам; недостаёт парного. Заменит гейты вида
   `distanceSquare < firstRadius * secondRadius * 2f` (`CovalentBondFormation:54`, `MoleculeGrowth:66`) —
   перемножение радиусов даёт площадь, а у молекулы вместо размера константа `MOLECULE_RADIUS = 20f`.
   После этого `Entity.radius` можно снимать: он помечен как временный и применим к трём видам из четырёх.
2. **`MoleculeGrowth`: связь с ближайшим атомом, а не с наименьшим `localId`.** Сейчас
   `firstFreeValenceAtomNode` — партнёр подлетает справа, связь возникает с атомом слева. Сайты считать
   ОДИН раз в `matchesMolecule` и класть в `Match` (сейчас выбор делается трижды, каждый раз с `!!`).
   После этого `firstFreeValenceAtomNode` удаляется.
3. **Протон — атом.** Он лежит в `SubAtom`, хотя физически ядро водорода-1, и из-за этого торчит в атомных
   правилах: `StarPPChain` (p+p→D) и `RecombinationReaction` (p+e⁻→H) принимают субъектом и атом, и частицу.
   Ровно ради них живёт временный `Entity.elementOrNull()`. Два варианта:
   - **малый**: сменить `Element.Proton.details.type` на `Atom`. Одна строка плюс перенос ветки
     `initProton` в `Atom.step()`; символ, метка, цвет, сейвы целы. Радиус поиска соседей вырастет
     5000 → 10000 (как у атомов). Спецкейс в `PhotoIonization` останется;
   - **полный**: протон = `HYDROGEN` с 0 электронов, `Element.Proton` исчезает. Убирает четыре костыля
     (`PhotoIonization`, `canGainElectron`, два в `RecombinationReaction`), но «протон» становится парой
     (элемент, заряд), а таблицы реакций ключуются по `Element` → ~5 мест сопоставления должны смотреть на
     заряд. Ломает сейвы.
4. **Переделка субатомов.** Частицы — не атомы, элемента у них быть не должно; звезда станет сложным
   объектом. Тогда же умрут `elementOrNull()`, последнее применение `ElementType` (выбор класса в
   `EntityGenerator`) и разделятся базовые классы правил по субъекту.


### Правило, по которому это разводилось
**Не хранить то, что выводится.** Координаты не в `AtomNode`: сломается структурное равенство графа (оно
служит ключом кэша и ответом «та же молекула?»), а `merge`/`split` перенумеровывают узлы — сохранённое
протухнет. По той же причине `MolecularAtom` обязан остаться ПРОЕКЦИЕЙ: структура из графа, координаты из
состояния. Класть в состояние готовый `List<MolecularAtom>` нельзя — `freeValence`/`isotope`/`radius`
станут копиями графовых данных и протухнут при ионизации и при усилении связи.


## Открытые вопросы

### Химия малых молекул
- **Замещение / метатезис / присоединение** (`A–B + C → A–C + B`) — основа органики (горение `CH₄+O₂`, гидрирование
  `HC≡CH→этан`). Отдельный слой с **гейтом по энергии активации** (иначе всё мгновенно сваливается в глобальный
  минимум — нефизично и комбинаторно взрывается). НЕ встраивать в `MoleculeGrowth` (тот — чистая ассоциация без
  разрыва связей).
  Живой пример, зачем этот слой нужен: игрок собирает `H–O–O–O–H` (триоксидан — вещество реальное, в реестре есть),
  и в модели цепочка БЕССМЕРТНА, тогда как в природе живёт миллисекунды. Распад идёт не разрывом, а
  перегруппировкой `H₂O₃ → H₂O + O₂`: тратим слабую O–O (1.51 эВ), получаем сверхпрочную O=O (5.16) — цепочка
  «расстёгивается» сама. Тот же расчёт объясняет, почему воздух это O₂, а не полимерный кислород, и почему
  полиоксидов длиннее H₂O₄ не наблюдали.
- **Гетеролитический распад / ионы-осколки** — сейчас распад только гомолитический (нейтральные радикалы). Для ионов
  делить электроны по электроотрицательности (данные — энергии ионизации по Z).
- Ионы-реагенты; зум/LOD рендера.

### Каноникализация
Наивная (перебор, гард ≤ 9 узлов: 9! ≈ 363k — мгновенно, 10! на порядок дороже) — **сделано**. Открыто: переход на
**Морган-подобный EC** (расширенная связность + разрыв ничьих по типу/заряду/кратностям), когда молекулы перерастут
гард; точная граница. Полимеры каноникализировать не надо — идентичность = последовательность (уже канонична).

### Идентификация: ключ → смысл
Канон отвечает «равны ли молекулы», но смысла не несёт. Лестница: формула (бесплатно) → канон (точная идентичность,
изомеры) → **классификация по функциональным группам** (`–OH`→спирт, `–COOH`→кислота, пептидная связь→белок; тот же
подграф-матчинг, что и реакции — один движок) → **реестр имён**. Открыто: когда вводить классификацию — сразу или
после реестра точных имён?

### Таксономия: остатки ElementType
`Species` удалён — вид материи теперь выражен запечатанной иерархией `Entity`: `Atom` / `SubAtom` / `Star` /
`Molecule`, и `when` по ней исчерпывающий. Тег `Details.type` дожил в трёх местах: каталог `ElementDetails`,
методы самого `Element` (символ, метка, лестница, `canGainElectron`) и `EntityGenerator`, где по нему
выбирается класс сущности. Последнее уйдёт вместе с переделкой субатомов (п. 4 «Ближайшей очереди»):
частицы перестанут быть «элементами», и выбирать класс станет не по тегу.

### Стадия 3 — полимеры / жизнь (отдельная эпоха)
Идентичность полимера = **последовательность** (`ATGC…`/аминокислоты; граф-каноникализация не нужна). Репликация/
транскрипция/трансляция — правила высшего уровня. Дальше: компартменты (мембраны), автокаталитические сети и —
фронтир — **эмёрджентная** самокопирующаяся эволюция. NB: репликацию НЕ хардкодить, иначе это анимация жизни, а не
жизнь. Вирусы — не «первая жизнь» (паразиты, нужен хозяин); реалистичный старт — самокопирующийся полимер (RNA-мир)
или протоклетка.

## Что модель осознанно НЕ покрывает
- **Озон O₃** — центральному O нужна валентность 3 (формальный заряд `+`, делокализация ~1.5); фиксированная октетная
  `valence()` + отсутствие per-atom заряда этого не выражают (наивный рост дал бы неверный линейный бирадикал
  `•O–O–O•`). Реальный O₃ собирается `O + O₂` только при подводе энергии, а не эмёрджентно. → курируемый спецслучай;
  починится вместе с per-atom зарядом (см. выше).
- **МО-экзотика** — октет/валентность лишь приближение. Реальный C₂ двойной (наше насыщение даёт тройной),
  парамагнетизм O₂ октет не объясняет. Для химии жизни приемлемо (C₂ не встречается) — МО-теорию не тянем.

## Ориентиры (не зависимости)
- **InChI** — золотой стандарт каноникализации (Морган-подобная нормализация + каноническое мечение; слой связности
  `c…` различает изомеры, `InChIKey` — 27-символьный хеш). C-код, не KMP/Wasm-дружелюбен и избыточен для наших
  крошечных молекул → держим ориентиром. [IUPAC/InChI Trust](https://github.com/IUPAC-InChI/InChI).
- **MOL/SDF (CTfile)** — индустриальный текстовый формат сериализации графа (atom block + bond block + `M CHG`/`M ISO`);
  прямое соответствие `AtomNode`/`Bond`. Потенциальный путь импорта/экспорта и вход для InChI. Наш формат — JSON-DTO.
- **nauty** — общая каноническая форма графа (если наивный перебор и Морган упрутся).
